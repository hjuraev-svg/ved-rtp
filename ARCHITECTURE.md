# Архитектура

## Обзор

```
                    ┌──────────────────────────────────────┐
   браузер  ──────► │  web  (nginx :80 → хост :8090)       │
                    │  • отдаёт собранный React SPA        │
                    │  • проксирует /api  → api:8000       │
                    │  • проксирует /ws   → api:8000 (WS)  │
                    └───────────────┬──────────────────────┘
                                    │  один origin → нет CORS,
                                    │  нет смешанных кук
                    ┌───────────────▼──────────────────────┐
                    │  api  (FastAPI + uvicorn :8000)      │
                    │  • REST + WebSocket-хаб              │
                    │  • JWT, роли                          │
                    │  • вся бизнес-логика красных зон      │
                    └───────────────┬──────────────────────┘
                                    │  asyncpg
                    ┌───────────────▼──────────────────────┐
                    │  db   (PostgreSQL 16)                │
                    │  том db_data — переживает перезапуск │
                    └──────────────────────────────────────┘

                    том uploads — файлы документов
```

Три контейнера, запуск по цепочке healthcheck: `db` здоров → стартует `api`;
`api` здоров → стартует `web`. Поэтому `docker compose up` не показывает белый
экран, пока база ещё поднимается.

## Ключевые решения

### Одна сущность «Сделка» вместо графа документов

В реальном ВЭД одна заявка может породить несколько контрактов, а контракт —
несколько отгрузок. Полная нормализация дала бы точную модель и неудобный
интерфейс: счётчики на дашборде перестали бы складываться в понятные числа.

Взята модель **одна сделка = одна отслеживаемая партия**, проходящая 18 этапов
последовательно. Это ровно то, что показывает исходный Excel: каждая плитка —
количество сделок на этапе. Если позже понадобится дробление партии, добавляется
`parent_deal_id` без переписывания дашборда.

### Производные значения не хранятся

`days_in_stage`, `is_overdue`, `docs_ready_pct`, `checklist_done_pct`,
`eta_slip_days` вычисляются при каждом запросе в `services.py`. Ничего не
кэшируется и не денормализуется.

Причина: денормализованный счётчик рано или поздно расходится с фактами —
из-за пропущенного пересчёта, отката транзакции или прямой правки в базе.
При 18 этапах и нескольких сотнях активных сделок пересчёт стоит один запрос,
а доверие к цифрам — важнее.

Массовые списки используют `bulk_progress()`: проценты по документам и
чек-листу для всей страницы считаются двумя агрегатными запросами, а не N+1.

### Красная зона — это правило этапа, а не поле сделки

`Stage.sla_days` редактируется из интерфейса. Логика в `is_overdue()`
специализирована там, где лист «Описание блоков» задаёт особое правило:

| Этап | Правило | Почему не «время на этапе» |
|---|---|---|
| 15. Растаможка | **рабочие** дни от подачи до выпуска | в листе прямо сказано «свыше 3 рабочих дней»; выходные не вина брокера |
| 12. В пути | ETA прошла без прибытия, либо ETA сдвинулась | груз в море 40 дней — это норма, а не простой |
| 9. Производство | факт готовности против плана | важен срыв срока, а не длительность |
| остальные | время на этапе > `sla_days` | |

Добавить новое правило — одна ветка в `is_overdue()` и запись в `_alert_for()`.

### Реальное время: широковещательный сигнал, а не дельты

Сервер не рассылает изменённые объекты — он рассылает факт «что-то изменилось»
(`deal.moved`, `document.updated`, …). Клиент перезапрашивает то, что открыто.

Так проще и надёжнее: не нужно поддерживать инкрементальное слияние состояния на
клиенте и разбирать конфликты порядка сообщений. Дашборд — это ~30 КБ JSON,
перезапрос дешевле сложности.

Хук `useLiveData(fn, deps, filter)` берёт это на себя: компонент объявляет, что
грузить и на какие события реагировать. `filter` не даёт странице документов
перезагружаться из-за чужого комментария.

Хаб (`realtime.py`) держит соединения в памяти одного процесса. При
масштабировании `api` на несколько реплик единственное место для правки —
`Hub.broadcast` (заменить на Redis pub/sub); вызывающий код не меняется.

### Авторизация WebSocket через query-параметр

Браузерный `WebSocket` не позволяет задать заголовок `Authorization`. Токен
передаётся в query и проверяется **до** `accept()` — при неверном токене
соединение закрывается кодом 4401, обработчики не запускаются.

### Справочники — код, данные — база

18 этапов, 24 пункта чек-листа и 9 типов документов лежат в `reference.py`,
а не в миграциях. `seed_reference()` идемпотентен и выполняется при каждом
старте: описательные поля обновляются из кода, а операционные настройки
(`sla_days`, `responsible`, `frequency`) записываются только при первом создании
и потом принадлежат пользователю.

Это значит: правка формулировки блока — правка одной строки в `reference.py` и
`docker compose up -d --build`, без миграций и без потери настроенных нормативов.

### Пароли без внешних зависимостей

PBKDF2-HMAC-SHA256, 240 000 итераций, соль на пользователя — из стандартной
библиотеки. Для внутренней системы этого достаточно, а связка `passlib`+`bcrypt`
известна конфликтами версий, которые ломают сборку на ровном месте.

### Валидация email намеренно мягкая

Строгий RFC-валидатор (`EmailStr`) отвергает special-use домены — в том числе
`.local`, на котором работают учётные записи по умолчанию. Используется простая
проверка формата, чтобы система не отказывалась заводить пользователей на
собственном домене.

## Схема данных

```
users ──┬─< deals >──┬── stages (18, справочник)
        │            ├── suppliers
        │            │
        │            ├──< stage_events        история переходов + время на этапе
        │            ├──< deal_checklist  >── checklist_templates (24)
        │            ├──< deal_documents  >── doc_types (9)
        │            ├──< quotes          >── suppliers
        │            ├──< claims
        │            └──< comments
```

`deal_checklist` и `deal_documents` материализуются при создании сделки — по
строке на каждый пункт шаблона. Это позволяет отмечать, комментировать и
прикреплять файлы к конкретному пункту конкретной сделки, а `%` готовности
считать обычным агрегатом.

`stage_events` — единственный источник данных для аналитики цикла: время на
этапе фиксируется в момент перехода, поэтому история остаётся верной, даже если
нормативы позже поменяют.

## Устройство фронтенда

Осознанно без внешних библиотек кроме React: нет роутера, нет UI-кита, нет
библиотеки графиков, нет Tailwind.

* **Роутинг** — хеш-роутер на 15 строк (`useHashRoute`). Побочный плюс: nginx не
  нужно ничего знать о маршрутах, `try_files` хватает.
* **Стили** — обычный CSS с переменными; тёмная и светлая темы переключаются
  одним `data-theme` на `<html>`.
* **Графики** — SVG вручную (столбцы времени этапов, спарклайн по неделям).
* **Загрузка данных** — `fetch` + `useLiveData`.

Причина: у системы длинный срок жизни и мало экранов. Каждая зависимость — это
будущее обновление, ломающее сборку. Итог — сборка из ~5 пакетов, которая
соберётся и через два года.

Файлы документов скачиваются через `fetch` с заголовком `Authorization` и
`URL.createObjectURL`, а не прямой ссылкой — иначе токен утёк бы в историю
браузера и логи прокси.

## Что стоит добавить при росте

| Потребность | Куда смотреть |
|---|---|
| Несколько реплик `api` | `Hub.broadcast` → Redis pub/sub |
| Эволюция схемы без потери данных | Alembic вместо `create_all` |
| Уведомления о красной зоне в Telegram | подписка на события хаба |
| Импорт истории из старых Excel | скрипт рядом с `seed.py` |
| Внешний доступ | TLS на nginx, `JWT_SECRET` из секрет-хранилища, убрать проброс порта `db` |
